The vuln

I quickly noticed something wrong in the options of the menu :

else if (choice == '3') {
            g->rules->destroy(g->rules);
            puts("Choose the rules :");
            puts("- [1] - Standard");
            puts("- [2] - Highlife");

In this option the g->rules is immediately freed but then since the default case of the switch never allocates something back and doesn’t nullify the g->rules pointer, if we type anything but 1, 2 or 3 we get a dangling pointer !

    

I also noticed that when a new grid is created the list of rows is not initialised, this means that we can leak heap chunk memory by calling next_step to fetch a freed chunk from the top of the tcache. Since we can force a g->rules struct to be freed (and so put it in the tcache) and that it contains the address of free from libc we can leak both libc and heap address (though we’ll actually not need heap address). Here’s the plan :

  1. Call option 3 (Change rules) and use an invalid option to cause g->rules to be freed

  1. Call option 1 (Next step) to trigger next_step and so the allocation of a new Grid struct using the old chunk of g->rules.

  2. Since memory allocated for the list of rows in Grid struct is not reset, it still contains function pointers present in g->rules struct (among them is a pointer to free in the libc). Calling option 1 draws the grid with 0s and 1s corresponding to the binary representation of unreset data present in the chunk. This is our leak !

Let’s write the code to trigger and parse this leak !

Write primitive ?

This very usefull write primitive let’s us modify the grid’s content bit by bit (thus the memory of the struct), it will be more than enough !

void change_cell(Grid g, int i, int j) {
    int state = g->get_cell(g, i, j);
    if (state == 1) g->kill(g, i, j);
    else g->make_alive(g, i, j);
}

How to trigger ?

The idea here is to use the fact that g->rules and g now live both in the same memory chunk at the same time. So we can modify function pointers inside the Rules struct by modifying the Grid with the above write primitive. The plan is as follow :

  1. Calculate binary representation of the address of a one gadget.

  2. Use option 2 (Change cell) to modify the bits of the 6th row of the Grid (corresponding to the 8 bytes address of PrintRulesFn function pointer in Rules struct) to write gadget address.

  3. Use option 4 (Display Rules) to trigger code execution

After a few tries, I realised that non of the one_gadget worked so I decided to build a call to system(“/bin/sh”) instead. I noticed that at the moment of the call to PrintRulesFn the rdi register contains the address of the first row of the Grid. So I can manipulate its content the same way as I did with the function pointer. Here I’ll write the bytes corresponding to "/bin/sh".

Final script :
